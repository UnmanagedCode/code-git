# Gotcha: merge, rebase and the sequencer

The merge / rebase / conflict ops (`src/git/sequence/`, `src/git/ops/head.js`, `src/git/remote/integrate.js`). Rules and tables: `docs/merge.md`. Each fact below is pinned by `tests/sequence-git-probes.test.js` (git 2.55).

- **`--continue` launches the editor; `GIT_EDITOR=:` keeps git's prepared message.** With `BASE_ENV`'s `GIT_EDITOR=false`, `rebase --continue` after a resolved conflict fails ("problem with the editor 'false'"). git recognises `:` as "no editor" and commits the message it prepared (the picked commit's, a merge's). Every `head.continue` / `head.skip` sets it in its op env.
- **Continue wordings** (`LC_ALL=C`): an empty cherry-pick or revert exits 1 with "nothing to commit" (stdout, from status) or "The previous cherry-pick is now empty" and stays in progress; a rebase with unstaged changes prints "You must edit all merge conflicts and then mark them as resolved using git add" (exit 1). A `merge --continue` or `cherry-pick --continue` with an unstaged change in another file just commits what is staged. A rebase whose resolution leaves the commit empty drops it (exit 0).
- **During a rebase stage 2 ("ours") is the onto side and stage 3 ("theirs") the commit being replayed** — the reverse of a merge's intuition. `--ours` / `--theirs` and `:2:` / `:3:` follow the stages, so code-git labels by stage and names the sides per operation (`sideLabels`).
- **`REBASE_HEAD` exists at a conflict stop and at an `edit` stop** (it names the commit being applied), **and stays behind once a rebase finishes from an `edit` stop on the todo's last line** (a later pick removes it). A rebase is detected from its state directory, never from `REBASE_HEAD` alone: `rebase-merge/` (merge backend) or `rebase-apply/` holding `rebasing` (apply backend; without it, `rebase-apply/` is `git am`'s). The step files differ: `msgnum`/`end` vs `next`/`last`. `head-name` is `detached HEAD` for a rebase of a detached HEAD; `orig-head` is the tip before the rebase (the undo).
- **`rev-parse --git-path X --git-path Y` prints one path per line**, and a git dir may hold a newline: ask for one (`rebase-merge`) and derive its sibling (`rebase-apply`) by replacing the last segment. A linked worktree's paths are per-worktree (`.git/worktrees/<w>/rebase-merge`, absolute).
- **`cat-file --batch-check` resolves `MERGE_HEAD` like any revision**: with the pseudo-ref absent, a branch or tag of that name answers instead (git warns about such names). Verifying the pseudo-ref as a file would break reftable repos, where `CHERRY_PICK_HEAD`, `REVERT_HEAD` and `REBASE_HEAD` live in the ref store (only `MERGE_HEAD` and `FETCH_HEAD` stay files). Accepted, documented.
- **An empty todo is "nothing to do" (exit 1); an all-`drop` todo is not**: git runs it and resets the branch to the upstream (exit 0). `rebase.interactive` refuses an all-drop request itself (`BAD_PARAMS`), which is the only guard.
- **`git merge` exits 2 for local changes in the way, 1 for conflicts; `git rebase` exits 1 for conflicts and for untracked files in the way**: tell the latter apart by the unmerged paths (`rebase()` aborts only the second).
- **`merge --squash` stages and writes `SQUASH_MSG`, but no `MERGE_HEAD`**: its conflicts are unmerged paths with no operation (nothing to `merge --abort`); the commit box concludes it. `SQUASH_MSG` lists every squashed commit (`commit <oid>`, `Author:`, the indented message) and may hold comment lines: `git stripspace -s` reads it as git's own cleanup would.
- **`rebase.backend` and `rebase.rebaseMerges` are config too**: a repo's `backend=apply` puts the state in `rebase-apply/` and changes the stop files; `rebaseMerges=true` would recreate merges. `REBASE` pins both on every rebase; a range with merges is refused (`HAS_MERGES`, from `rev-list --merges --count`) rather than flattened.
- **`GIT_SEQUENCE_EDITOR='cat >'` with the todo on the exec's stdin** writes git's todo byte for byte: git runs the editor through `sh -c '<editor> "$@"'` with its own stdin inherited, and hooks (pre-rebase, post-rewrite) never read it (git gives them no stdin, or their own). No temp file, no tty, a constant editor string.
- **`commit-tree` ignores `commit.gpgSign`**, unlike `commit`: a carrier passes `-S` itself when the config says true (`config --type=bool`). It takes `--end-of-options` before the tree.
- **`pick <carrier>` fast-forwards onto the carrier** when nothing before it changed: the carrier (X's tree and parent, X's author, a new message) becomes the branch's commit as is. That is why a reword or squash message never needs an editor, and why it survives a conflict stop and a reload.
- **`--empty=drop` (git ≥ 2.26)** drops a pick that became empty instead of stopping on it; without it, `-i` would stop there and ask.
- **`restore --source=<tree> --worktree -- <p>` on an unmerged path writes the file and leaves the index's stages**: it reads the tree into an in-core index only. That is how `conflict.save` writes a resolution without resolving it (the tree is a `mktree` chain holding only the new blob). Plain `restore --worktree -- <p>` without a source refuses an unmerged path.
- **A stage-0 entry fed to `update-index --index-info` replaces every unmerged stage of its path** (a gitlink's submodule checkout is not touched). `-z` must come before `--index-info` ("option 'index-info' must be the last argument").
- **`checkout --ours|--theirs -- <p>` then `add -- <p>` takes a side for a file; `rm -f -- <p>` for the side that deleted it** (`checkout --theirs` of a path theirs deleted fails: there is no stage 3).
