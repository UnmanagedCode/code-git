# Gotcha: links to and from code-review

Reference: [docs/protocol.md → UI routes](../../docs/protocol.md#ui-routes) and [→ Links to code-review](../../docs/protocol.md#links-to-code-review). What is not obvious from the code:

- **A cold-load jump fails if it is requested at once.** The graph starts loading only once the repo summary is in (`useGraph`), and `loadUntil` (`frontend/src/state/graph.ts`) answers `'end'` while the graph is `idle`. `GraphPanel` serves a pending jump on mount, so a jump requested before the first snapshot shows "Not in the visible graph". `followLink` (`frontend/src/features/links/inbound.ts`) therefore subscribes to `graphStore` and calls `requestJump` only once the tab's graph is `ready`. The wait must always end: a graph that turns `error`, the tab's close, a refused summary (no summary, not loading; the graph never starts), and a newer link each drop it, so a wait never outlives its tab. A wait left behind would jump unasked when the tab is reopened later and loads. App's effect cleanup must **not** call `cancelLink`: `main.tsx` renders under `<StrictMode>`, whose dev double mount runs the effect twice. The first run consumes (strips) the link, its cleanup would drop the wait, and the second run finds no link to restart it.
- **`requestJump` closes only a diff.** A shown History or Reflog panel keeps the graph unmounted, so `followLink` clears the slot first: `closeDiff` for a diff (`hidePanel` alone would leave its state in `diffStore`), else `hidePanel`.
- **The link keys are one-shot, and the order in `App.tsx` matters.** `consumeLink` strips `commit` / `path` with `replaceState` *before* `dispatchTabs`. Otherwise the tab store's subscription runs `writeRoute`, which strips them with `pushState` and leaves a standalone history entry that still holds the link (Back would re-apply it).
- **Embedded, the strip also rewrites cc's entry.** The bridge reports every in-frame `pushState` / `replaceState` route, and cc's hash mirror replaces its own current entry with it. So cc's Back / Forward / reload never re-apply a link. A second identical click in code-review still steers: cc compares the new subpath to the frame's last *reported* (stripped) one, and they differ.
- **Outbound is a fragment-only top navigation.** `navigateTop` (`frontend/src/lib/host.ts`) does `window.top.location.assign(<cc pathname + search> + '#plugin/…')`. Same document, so cc does not reload: its `hashchange` switches the view. This is the one sanctioned top navigation. The menu runs `onSelect` only, and `guards.test.ts` bans `href={` outside `components/ui/` and `.href =` outside `lib/download.ts`, so a menu item cannot be an `<a>`. Never assign `location.hash` (also guarded).
- **Closing code-review's view does not return to code-git.** cc's close steps back only over entries cc pushed itself. The browser's Back works.
- **The plugin id lives in the backend only** (`CODE_REVIEW_PLUGIN`, `src/conductor/integrations.js`). The UI learns it from `GET api/integrations` and fetches it only when embedded (`loadIntegrations`). An older cc without `GET /api/plugins` is `CONDUCTOR_UNAVAILABLE`, not "no code-review"; the UI then hides the items and warns.
- **HEAD goes as its full oid** in `range=<base>...<head>`, never `HEAD`: a HEAD that moves before code-review resolves it becomes a reported mismatch, not a silently different range. A range is offered only when `chainOf` (`frontend/src/features/sequence/actions.ts`) finds one first-parent chain whose newest commit is HEAD. With a merge or root commit in the selection, `base...HEAD` would not equal the selection.
- **The frontend mirrors two backend rules** it cannot import: `OID_RE` and `assertPath` (`src/git/validate.js`), copied into `readLink` (`frontend/src/lib/route.ts`). The backend still re-validates `rev` / `path` when the history is read; change both sides together.
- **Harness:** `links.mjs` fakes cc with a `page.route`-served `host.html` framing the app on the backend's origin, plus a stub `/pluginBridge.js` that defines `ccBridge` only when framed.
