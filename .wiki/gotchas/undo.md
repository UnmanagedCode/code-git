# Gotcha: undo and redo

The backend undo (`src/git/undo/`, reference: `docs/undo.md`).

- **`reset --keep` refuses in two one-line shapes** (git 2.55, LC_ALL=C): `error: Entry '<p>' not uptodate. Cannot merge.` (a local change to a file the move rewrites) and `error: Untracked working tree file '<p>' would be overwritten by merge.` — neither has the indented list `parseConflictFiles` reads, so the keep step parses both itself (`KEEP_REFUSED_RE`, `src/git/undo/steps/head.js`). Pinned by `undo-git-probes.test.js`.
- **`reset --hard` overwrites untracked files silently**, and writes through an untracked symlink standing for a directory: the hard step lists the paths the target tree (and, for undo, the snapshot and its index commit) adds over the current one (`diff-tree --diff-filter=A`) and refuses an untracked file there (`ls-files --others`) or a blocked leading directory (`assertNotBlocked`) first.
- **One `update-ref --stdin -z` transaction for all of a step's refs**: `start` … `prepare` / `commit`, each line with its old value, so one ref that moved writes nothing. Its CAS wordings: "but expected", "reference already exists", "unable to resolve reference" (`CAS_RE`). Deleting a branch through it leaves `branch.<name>.*` config behind (`branch -d` removes it), so the refs step runs `config --remove-section` (exit 128 = no such section).
- **The discard snapshot is a temporary index, not `stash create`**: `stash create` holds tracked changes only, and a discard deletes untracked files too. `update-index --add --remove -z --stdin` over the paths reads their worktree content, mode and symlinks, and leaves a deleted file out; `restore --source=<snapshot> --worktree` then writes an untracked path back and deletes a tracked one the snapshot lacks. `GIT_INDEX_FILE` from `rev-parse --git-path`, emptied afterwards (no filesystem access to delete it).
- **`created.not` is what keeps the pushed rule honest**: a merge's `not` includes the merged commit (merging `origin/main` would otherwise count `origin/main`'s own commits as created and refuse); a rebase's is its onto (the old commits are not "created" either); `commit.create` concluding a merge reads `MERGE_HEAD` before committing. `--not --remotes` goes **after** `--stdin` in argv: it negates only the remotes, not the stdin tips.
- **Preflights read a projection, not git, for what earlier steps change**: a plan's steps can depend on each other (checkout-with-create: switch then delete on undo; the remote checkout's ff: refs then switch on redo), so "every preflight before any apply" needs each preflight to see the state the earlier steps will leave (`projection` in `src/git/undo/engine.js`). Checked-out = another checkout's `%(worktreepath)`, or this checkout's *projected* HEAD.
- **A mixed reset's index is a tree, not a stash**: `write-tree` before the reset (fails on unmerged entries → `indexTree: null`); undo is `reset --soft` + `read-tree` (no `-u`: the worktree is untouched), checked first with `diff-index --cached --quiet <tree>`.
- **An id mismatch does not clear the slots**: the request is stale (the UI read `undo.state` before another write), not the entry. A preflight `UNDO_STALE` does: the checkout changed, so that entry can never run.
- **A recorded upstream is repo config, not a ref**: `%(upstream)` echoes `branch.<b>.merge` as-is when `branch.<b>.remote = .` — `merge = --help` makes it `--help`, which `for-each-ref` took as an option (exit 129). The refs step passes on any full refname (not only `refs/heads/` and `refs/remotes/`: a fetch refspec `+refs/heads/*:refs/other/*` makes `refs/other/main` an upstream git sets and tracks) and lets git judge it: `--set-upstream-to` exits 128 on a tag or a `refs/remotes/<r>/…` of an unconfigured remote, which becomes a warning, since the transaction already restored the ref; `refEntries` puts `--end-of-options` before its patterns.
- **A stash undo writes a recorded state, never a stash apply**: popping W back would merge, could conflict, and cannot delete the untracked files a pop created. The `worktree` step instead runs a two-way `read-tree -m -u <from> <to>` on a temporary index holding only the op's paths (`writeCheckoutState`, `src/git/stash/snapshot.js`): it writes modes and symlinks, deletes removed paths with their emptied directories, and refuses an untracked file in the way — the rest of the worktree is invisible to it. `read-tree <tree>` leaves no stat data, so `update-index --refresh` must run first (else the merge's up-to-date check fails); **`-q --refresh` exits 0 even when a file differs**, so it runs without `-q` (exit 1 → `UNDO_STALE`). Pinned by `undo-git-probes.test.js`.
- **`worktreeTree` takes file paths only**: `update-index --add` refuses a directory, so stash.push records its state over `savedPaths`' expanded `files` (never the user's directory pathspec), and drops the state — so no plan — when the stored stash holds a path outside them.
- **The worktree step checks the state "as the direction starts", not "as the step starts"**: in stash.branch the `head` switch runs between, so the record keeps a third state, `mid` (after the switch, before the apply). Undo writes `mid` before switching back (git would refuse to switch over the applied changes); redo's switch reproduces `mid` from `before`.
- **`stash store` puts an entry at `stash@{0}` only, and takes no `--end-of-options`** ("requires one <commit> argument"): an undone drop of an older entry comes back first in the list (R1); the argv scan allows its final full oid without the marker.
- **What `git remote remove` clears is re-read, not assumed**: it removes the section, every `branch.<b>.remote` / `.merge` and `branch.<b>.pushRemote` naming the remote, and `remote.pushDefault` when it names it — from the repo's own config only. **git picks the branches by their *effective* `branch.<b>.remote` / `.pushRemote` (merged scopes) but unsets `.remote` and `.merge` in `.git/config` only**: a global, included or `config.worktree` `branch.main.remote = origin` beside a local `merge` loses just the local merge. So remote.remove records the diff of the local branch keys before and after (`branchKeys`), never "branches whose local remote names it", and the redo predicts git with the same rule (`clearableKeys`: effective picks, local keys). Reading any of this across scopes instead would make a global key look like "set again" to the undo (never restorable) or like a missing key to the redo. Pinned by `undo-git-probes.test.js` and the scope round trips in `ops-undo-remote.test.js`.
- **A remote written back lands at the end of `.git/config`**: git (2.55) drops a section it empties, and `config --add` appends a new one; so the undo of a remove keeps each key's values in order but not the file's interleaving. The undo tests' snapshot compares config by key (stable sort, `tests/_undoWorld.js`) for that reason. A *change* uses `config --replace-all <key> <first>` (in place) rather than `--unset-all` + `--add`, which would move the key to the end of its section.
- **Never `key=value` or `-c` for a url**: `writeRemoteConfig` passes each value as its own argument after the key — git stops parsing options there (a `-x` value is stored as `-x`), and the activity log's `redactArgv` masks only a whole-argument url.
