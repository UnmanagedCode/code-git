# Gotcha: talking to remotes

Fetch, pull, push and the remote config ops (`src/git/ops/remote.js`, helpers in `src/git/remote/`). Rules and tables: `docs/remotes.md`; the hostile-config table: `docs/architecture.md`.

- **`protocol.<name>.allow` beats `protocol.allow`, and `-c` beats every config file**, so `NET_CONFIG` (`-c protocol.ext.allow=never -c protocol.fd.allow=never`) wins over a repo's `protocol.allow=always`, `protocol.ext.allow=always` and an `insteadOf` rewriting a url to `ext::sh -c …` (git: "transport 'ext' not allowed"). Only the environment's `GIT_ALLOW_PROTOCOL` overrides it (verified with git 2.55) — the System's, not the repo's, and setting it ourselves would restrict every transport (an empty value allows none).
- **A 403 is "unable to access … returned error: 403"**: the unreachable pattern `unable to access` also matches it, so the credential rules are checked first (`classifyRemoteFailure`'s order). Likewise a credential helper's rejected credentials print git's `could not read Username … terminal prompts disabled` line *and* `Authentication failed`: credentials before prompt.
- **git 2.48+ fetch creates `refs/remotes/<r>/HEAD` itself** (`remote.<r>.followRemoteHEAD`, default `create`): a symbolic ref the first fetch adds. It is the one symbolic tracking ref allowed (`isHeadAlias`: the destination pattern with `HEAD` for `*`, pointing into the same pattern) and never reported as "resolved".
- **git 2.55's fetch skips a symbolic tracking ref** (live or dangling: neither it nor its target is written, silently), unlike push, which writes through one. The live-symref refusal before a fetch does not rely on that; a dangling one still comes to life when the fetch creates its target by other means — e.g. `origin/new → refs/tags/v9` and the fetch follows tag `v9` — which is what `symrefsResolved` reports. A live one is refused by the next fetch.
- **`--no-prune-tags` and an explicit `--prune`/`--no-prune` on every fetch**: `fetch.prune`, `fetch.pruneTags` and `remote.<r>.prune(Tags)` would otherwise delete tracking refs or local tags with no confirmation.
- **`rebase.updateRefs=true` moves other branches**: every local branch pointing at a commit in the rebased range is rewritten with it (a `code-conductor/*` one included). Every rebase pins it off, with `rebase.autoStash` and `rebase.autoSquash`.
- **Pull is not `git pull`**: `pull.rebase=interactive`, `pull.ff=only` and friends are never read; the pull fetches through `fetchRemote` and integrates an explicit oid (never `FETCH_HEAD`, which a cancelled or multi-remote fetch can leave partial).
- **`git merge` exits 2 when local changes would be overwritten, 1 on conflicts**; the merge pull accepts 0 and 1, so `guardOverwrite` (which acts on a `GIT_FAILED`) still turns exit 2 into `CHECKOUT_CONFLICT`. `git rebase` exits 1 for conflicts *and* for untracked files in the way ("could not detach HEAD"): tell them apart by the unmerged files, and abort either way (`rebase --abort` exits 128 when nothing is in progress).
- **`--force-with-lease=<ref>:` with an empty expect means "must not exist on the remote"**; with no `:<expect>` git would lease against the tracking ref, which a background fetch may have moved. `remote.push` always passes the oid the UI showed, never `--force` or a `+` refspec. A stale lease is rejected as `stale info`.
- **`ls-remote <remote> refs/heads/x` matches path tails**: `refs/heads/a/refs/heads/x` matches too. `remote.peek` keeps the exact name.
- **`git remote` lists a remote only from config keys**: a remote defined only by a legacy `.git/remotes/<name>` file is not listed until some `remote.<name>.*` key exists. `git remote remove` deletes only `refs/remotes/` refs its refspecs map (never `refs/heads`, even with a mirror refspec) and keeps a ref another remote also maps; it clears `branch.<b>.remote`/`.merge` from config whether or not the branch exists.
- **`git remote set-url <name> <url>` without an old url replaces the single value**, and fails ("multiple values") on a list: `remote.edit` refuses a multi-valued list before running it.
- **A push updates the local ref the fetch refspecs map every pushed destination to — tags too**, not just branches (git 2.55: `+refs/tags/*:refs/heads/t/*` makes `push origin v1` move local branch `t/v1`; a delete push deletes the mapped ref). So `push()` maps every destination and refuses a mapped ref outside `refs/remotes/` (`assertPushTracking`, sharing `assertUnder` with the fetch rule), except a ref mapped onto the pushed source itself.
- **`core.gitProxy` cannot be pinned with `-c`**: it is multi-valued and the *first* match wins, and the repo's config is read before command-line `-c`, so `-c core.gitProxy=none` loses (git 2.55). `GIT_PROXY_COMMAND` in the env (even empty) stops git reading the config at all. Accepted as a residual beside `core.sshCommand`. `remote.<r>.mirror` is a boolean (last wins), so `-c remote.<r>.mirror=false` does override it on each push.
- **The browser only ever holds masked urls; the undo journal holds raw ones.** `listRemotes` masks `urls` / `pushUrls`, `forTheWire` masks each undo record side, and `listSubmodules` / `submodule.init` mask `resolvedUrl`. The journal builds its plan from the raw result before the route answers (`journalAround`), so undo, redo and re-adding a removed remote restore the real password without the browser sending it. Never build a plan, or anything written back, from a wire copy.
- **`remote.edit` reads the mask echoed back as "unchanged"** only when it equals `maskUrl` of the raw list's single value; any other masked url (`isMaskedUrl`) is refused `BAD_URL`. A masked value skips `remoteUrl` in the params (`editedUrl`): a remote stored with git as `<transport>::<url>` fails `remoteUrl`, and its echoed mask must still reach the unchanged rule. Splicing the stored password into an edited url would send it to whatever host was typed. The multi-value check (`assertSingle`) runs before the mask check, so a multi-valued list still refuses `REMOTE_CONFIG_UNSUPPORTED`.
- **A submodule's `resolvedUrl` can carry a remote's password**: `git submodule init` resolves a relative `.gitmodules` url (`../sub.git`) against the default remote's url, userinfo included.
- **What a mask must find in a stored value or a git message**: any `<scheme>://` (git runs `git-remote-<scheme>` for any scheme, `1password://` included), a url anywhere in the value (`foo::https://user:PW@h/r`: `maskUrl` is unanchored), and in a text a password holding a space (git quotes the url whole: `'https://user:S3 CRET@h/r/'`). The text span (`textSpan` in `src/mask.js`) runs to the `@` ending the url's authority on that line — a strong end (host, then `/ : ? #`, a quote or a bracket) before a weak one (host, then whitespace), and a later end before the token's own when the password goes on past whitespace (the token's `@` may be inside it: `p@ss word@h/r`), never across another url, never from whitespace or a port's digits, never empty — because a greedy run to a line's last `@` would swallow a second url or `user@host` text. In a text a url starts only at a url boundary (`boundaryAt`): `remote.add` accepts `https://u:pw://x@h` and git quotes it back, so a `://` after a lone `:` must not bound the span.
- **Never search for a url's scheme with a regex**: `[A-Za-z0-9][A-Za-z0-9+.-]*://` unanchored backtracks over every long alphanumeric run (quadratic: a 400k-character url posted to `remote.edit` blocked the event loop for nearly a minute; a remote's stderr reaches `maskUrls` uncapped up to 1 MB). `src/mask.js` scans from each `://` instead (`nextUrl`), and `editedUrl` applies `URL_MAX` before `isMaskedUrl`. The timing tests in `tests/mask.test.js` and `tests/remote-credentials.test.js` pin it.
- **`redactArgv` masks by argument kind**: a `remote` / `config` / `submodule` / network command's argument is a url or a value (`maskUrl`, conservative: masks even a leading-space password); any other argument is free text (`maskUrls`): `maskUrl` would rewrite `…/pull/1: ping @alice` to `…/pull/1:***@alice`.
- **git prints a `git://` url's authority without its scheme**: `fatal: unable to look up user:pw@host (port 9418)` (git 2.55; `ls-remote`, `fetch`, `clone`, `push`; the userinfo-bearing host fails to resolve locally, `127.0.0.1` too). No url mask sees it, so `remoteUrl` refuses userinfo in a `git://` url (the protocol cannot authenticate anyway; a `%40` counts as its `@`), and `maskUrls` masks that look-up line (`maskLookups`) for a remote set with git. The host is printed decoded, so a password may hold ` (port ` or the look-up text: the host runs to the first ` (port ` or next look-up *after its first `@`*, never the first one on the line. A password with a raw `@` is the other shape git prints unquoted: it splits the userinfo at the first `@` and shows the tail as the user name — a documented residual.
- **git percent-decodes a url's userinfo** (ssh, git and http transports): `ssh://A%3AS@H` and `ssh://A:S%40H` both hand `A:S@H` to ssh. A mask needing a literal `:` and `@` leaves those raw, so `delimAt` in `src/mask.js` reads `%3A` (any case) as the userinfo `:` and `%40` as its `@`, in values and texts alike.
- **git's trace output prints a scheme-less `user:pw@host`, trace2's too**: `GIT_TRACE`'s `trace: run_command: ssh … user:pw@host`, and trace2's `child_start` of the same plus a `def_param` of a config url — trace2 redacts only `scheme://` urls (git 2.55; `GIT_TRACE2_REDACT=0` shows more). `BASE_ENV` sets `TRACE_OFF` (`src/git/runner.js`): every trace and trace2 switch `0` (the env beats a `trace2.*Target` in the System's global config), trace2's config-param and env-var lists empty, both redactions `1`; `PROTECTED_ENV` keeps an op from changing any of them.
