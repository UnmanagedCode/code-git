# Extension points

How later cards plug in without editing each other's files. The table of what to create and where to register: `docs/architecture.md` → Extension points. The decisions:

- **Registries are explicit lists, not self-registration.** `PANELS` (`frontend/src/shell/panels.ts`), `ACTIONS` (`frontend/src/shell/menus.ts`) and the `buildRegistry` list (`src/git/ops/index.js`) each import their entries. A feature module calling `registerPanel()` at import time would create an import cycle with the registry module (TDZ at load). A feature adds one import + one list entry; parallel cards conflict only on adjacent lines.
- **Ops, not routes.** A new git capability is an op file; `POST api/ops/:name` already handles target validation, cancel wiring and activity. Add a route file only for something that is not a git op.
- **`cancellable` is resolved once at load** (`buildRegistry`); the route and the activity log read the frozen definition. Default read → true, write → false; a non-boolean throws at load.
- **Write lock is per project, not per checkout** (`src/git/locks.js`): worktrees share refs and objects, so two writes on different worktrees of one project still serialize.
- **On-demand panels** (`PanelDef.onDemand`, `state/shownPanel.ts`): a panel such as the diff takes over its slot for one tab while `showPanel` names it, instead of each feature hand-rolling "replace the graph". `Slot` in `Shell.tsx` is the only reader; the shown id is per `tabKey`, pruned when the tab closes, and not persisted (a reload shows the graph).
- **Ops get `{target, journal}` as `run`'s third argument**: `target` for naming output after the checkout (`diff.patch` filenames), `journal` for the `undo.*` ops only; git still goes only through the bound `git`.
- **Undo registers on the op, not in a second table**: a write's own definition carries `undo(params, result) → plan` (`buildRegistry` checks it). The journal lives in the backend and the ops route wraps every op (`journalAround`), so no frontend `run*Op` needs to know about undo, and a write made from any surface clears the slots. A separate registry keyed by op name would let an op be renamed or removed without its undo noticing.
- **Per-checkout UI state** goes in a feature's own store keyed by `tabKey`; there is no central `RepoState` to edit.
- **Context-menu contexts** are free strings: `'tab'`, the diff's `'diff-file'` (a diff's file list row), the Changes panel's `'workdir-file'` (ctx `{tab, file, section}`) and the graph's (`CONTEXT` in `frontend/src/features/graph/contexts.ts`, with each ctx type; table in `docs/architecture.md` → Extension points). A later card adds write actions by appending a `MenuAction` list to `ACTIONS` with an `order` from the convention there — never by editing the graph's files.
- **`<ActionMenuItems>` renders inside a `DropdownMenuContent`**; a tab's menu is a controlled DropdownMenu opened by its ⋮ trigger or by `onContextMenu` (cc ships no context-menu component). For a menu at the pointer, `openContextMenu({host, …})` + `<ContextMenuHost host>`: one host per panel, named, because a menu opened from inside a modal dialog (the refs panel on a phone) must render inside that dialog's layer to be usable.
- **The press that opens a context menu can never run an item**: Radix's menu item synthesizes a click on a `pointerup` whose `pointerdown` it did not see, and a menu opened on a right-press (or touch long-press) can be placed under the pointer — a tall menu flipped upward in the phone Refs dialog put Hide under it. `openContextMenu` swallows (window, capture phase) the release that ends each press held at opening, plus a click from it; menus opened with no press held (keyboard, after a drop) are untouched. An offset would not do: any menu tall enough still lands under the pointer. Disarming never waits on a timer (a release lost outside the window, a release with no click, a late touch compatibility click): a new press of the *same* pointer ends its armed release and its armed click (a second finger must disarm neither for the first), a key ends an armed click (and only a click carrying the armed pointer's `pointerId` is swallowed: another finger's tap runs; a click with no `pointerId` is swallowed as the safe side), and window `blur` or `visibilitychange` ends everything.
- **The anchor moves before the menu opens**: `ContextMenuHost` sets the 1×1 anchor's position in a layout effect and opens on the next render, so Radix places the menu from the new position.
- **The graph hands the diff viewer stores, not callbacks**: `graphSelectionStore` (selection, top to bottom) and `fileIntentStore` (`seq` increases per click). Neither side imports the other's components.
- **`openWorkingTree(target, {amend?, focus?})` is the commit box's entry point**, not "show the right slot": below `lg` the slot is hidden (display none, still mounted), so the call opens the Changes dialog instead, and a focus request names which instance (slot or dialog) takes the focus — both may be mounted at once. The dialog is mounted by `WorkdirPanel`, not by the toolbar button, so it opens while a diff has replaced the graph.
- **The right slot shows one of Changes and the commit details, by the graph selection** (`changesInRightSlot`): both panels read the rule rather than a mode store, so a WIP click, Esc (clear) or `openWorkingTree` (which clears a commit selection) needs no extra state. The details' narrow dialog ignores it.
- **A context-menu action may move the focus** (`ContextMenuHost` remembers an element focused outside the menu while it is open and refocuses it on close): Radix's menu focus trap pulls such a focus back into the menu, and the close would then hand it to the hidden anchor.
- **`restoreFile(target, oid, path)`** (`features/workdir/entry.ts`) is the restore entry for a commit's details panel; it confirms first. The diff's `'diff-file'` menu offers it through `RESTORE_ACTION`, which reads the tab's pinned pair from `diffStore` rather than widening `DiffFileCtx`.
- **A `MenuAction.label` is a fixed string**, so items whose label names the file (the Changes row's "Ignore '‹name›'") are rendered beside `<ActionMenuItems>` by the feature, not registered.
- **One `ConfirmHost`**, mounted by the Changes panel (always mounted while a tab is open: the right slot is hidden by CSS, not unmounted). `confirm()` resolves false when another confirmation replaces a pending one.
- **Double-click is a menu action, not a handler per surface**: `MenuAction.primary` + `runPrimary(context, ctx)`. Chips, refs rows and later surfaces call `runPrimary`; what a double-click does is decided where the action is registered (`features/branches/actions.ts` Checkout; the graph's tag Jump), so a card that adds a better primary only flips a flag.
- **Submenus may be built from the ctx** (`children: (ctx) => MenuAction[]`): per-remote items ("Push to › origin / upstream") cannot be a static list. `resolveActions` builds and filters them per call; consumers only see `ResolvedAction` (arrays).
- **One toast surface, one helper**: sonner's `<Toaster>` is mounted once (`shell/Toasts.tsx`, beside `<App>`), and features call `trackOp` (`lib/opToast.ts`), never `toast()` directly, so every op's progress → outcome looks the same and every string is clipped. A dialog op passes `toastRunning: false` (the dialog shows busy and the refusal) and toasts only its success.
- **Branch-drop slots are reserved by order, not placeholders**: merge and rebase register at 100–199 (`features/sequence/actions.ts`); no disabled items stand in for missing ones.
- **The cc HEAD gate lives in the UI action, the rule in the backend**: `withCcHeadAck` decides whether a confirmation is shown (the shared `confirm()`: a plain yes/no, so it is the only branch confirmation that does not need the branch dialogs' in-dialog busy state and inline refusal); `assertCcHeadAck` refuses without `ccOwned` regardless, and a stale-refs refusal (`head: true`) reopens the same confirmation from the toast.
- **Stash dialogs live in one store and one host** (`state/stashDialog.ts`, `StashDialogHost` mounted by `Shell`), so any surface — a graph menu, the Changes header, the diff's hunk and line controls — opens the save dialog with a preset (`openStashSave(tab, preset)`) instead of owning a dialog. The line controls get an optional `onStash` prop (`SelectionBar`, `HunkActions`); `DiffPanel` decides when to pass it.
- **The diff header takes a `parentControl`** that replaces its parent select: the stash's view switch is passed in by `DiffPanel`, so `DiffHeader` stays free of stash knowledge.
- **A rebase's conflict policy is one function**: `onRebaseStopped` (`src/git/remote/integrate.js`) keeps the rebase in progress and answers `{outcome: 'conflicts', files}` — the same outcome a merge pull's conflicts give — for every caller of `rebase()` (a pull, a rebase start, an interactive rebase). `head.continue` / `head.skip` / `head.abort` take a stopped operation from there.
- **What is in progress is read, never remembered**: `operationState` reads git's pseudo-refs and state files on every `commit.state`, so the Changes banner survives a reload and shows operations started outside code-git. `runRefOp` reloads a loaded Changes panel after every ref op so the banner appears at once.
- **A submodule tab is only a target with `sub`**: every panel already sends its tab's target through `targetBody`, so nothing feature-specific changes for it. What a feature must decide is its key: per-checkout state by `tabKey`; state shared by a project's worktrees (refs-derived) by `refsKey`, which keeps a submodule apart; persisted graph prefs by `prefsKey`. Code that builds a target from parts (`{project: tab.project, worktree: tab.worktree}`) drops `sub` — pass the tab.
- **Submodule dialogs live in one store and one host** (`state/submoduleDialog.ts`, `SubmoduleDialogHost` mounted by `Shell`), like the stash's; the host also owns the exit watcher, so the pointer prompt follows every way a tab can close without each close path knowing about submodules.
- **Shortcuts are data, handlers only match**: every binding is a `Shortcut` in a feature's `keys.ts`, listed in `SHORTCUT_GROUPS`; handlers call `matches(e, KEY)` and `guards.test.ts` fails on any other read of `e.key` / a modifier field. So the shortcut sheet and the palette's shortcut column can never drift from what the keys do. Handlers keep their own ordering and context (the graph checks search before lane moves; row keys stay on their rows): the catalog says *what* is pressed, not *where* it acts. Click modifiers go through `pointerMods` for the same guard.
